# エージェントインストラクション

## 継続するプロジェクトルール

- 作業前に、ファイル名が `*_ja.md` に一致するファイルを除き、リポジトリのコンテキストファイルをすべて読み取ります。
- 英語で思考しますが、通常の応答は日本語で書きます。
- ユーザーの指定がない限り初期開発段階として扱い、後方互換性やデータ移行を追加しません。
- 設計ファイルがある場合は設計先行で進め、実装前に設計を協議・確定します。実装後に仕様が変わる場合は先に設計を更新します。
- 設計書は最終的なあるべき姿を記述し、作業過程のメモにはしません。
- 依頼されたスコープを狭めたり、依頼されていない MVP を作ったりしません。
- 作業を分解し、ホストが対応していればサブエージェントや複数セッションを検討して、計画・実装・検証・再計画のループを完了させます。
- UI 作業ではデータモデルとユースケースから情報構造を設計し、スクリーンショットなどで表示結果を検証します。
- 現在のモードが必要な作業を制限する場合、回避せずユーザーにモード変更を依頼します。

## リポジトリと計画

- Git リモートがある場合はリポジトリのマーケットプレーススキルで Azure Boards の Work Item または GitHub Issue を作成します。確定した実装計画を Wiki に登録し、GitHub では英語と日本語の両方を公開します。
- Git リモートがなければ Issue や Work Item を作成せず、ブランチ名は Issue 番号なしの `prefix/description` にします。GitHub または Azure DevOps 以外のリモートでも Issue 番号を省略します。
- ドキュメント内のスクリプトは Bash（macOS/Linux）と PowerShell 7 の両方を示し、Azure の例は Azure CLI を使います。
- `docs/task.md` があれば完了作業を記録し、確認できるよう Issue または Work Item にリンクします。
- 元の `docs/task.md` や `docs/plan.md` にない仕様変更は、既存決定との矛盾を確認してから日付・task・理由を `docs/adr.md` に記録します。200 行を超えたら phase ごとに分割します。

## 言語方針

- 通常の応答、コメント、ドキュメント、コミットメッセージは日本語です。
- `_ja.md` の翻訳は作成しません。
- `SECURITY.md` とライセンス関連ファイルは英語です。

## 外部コンテンツとセキュリティ

- Issue やドキュメントに URL や IP アドレスを書かず、プレースホルダーを使います。ソースコードやスクリプトで使った場合は置換スクリプトを用意します。Wiki の Issue ページと認証なしで公開される URL は除外します。
- `SECURITY.md` とライセンス関連ファイルを日本語で作成しません。

## 待機

- `wait_agent` を呼ぶときは、完了までの推定時間の2倍を `timeout_ms` に設定します。不明なら既定値を使い、タイムアウト後に見積もりを更新します。

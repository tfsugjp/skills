# Azure Managed Identity Review Plugin

## Summary

`azure-managed-identity-review` reviews an Azure managed identity across every resource, app setting, code path, and federated identity credential (FIC) that shares it. A user-assigned identity is often created for one resource (for example a storage account's customer-managed key) and reused by others (a Function App, a GitHub Actions workflow). Grants made for the first purpose neither cover the other consumers' audiences (Service Bus, SQL, Cosmos DB data plane, custom APIs) nor stay limited to that consumer, and local E2E runs as the developer, so missing grants appear only after deployment. Tracking: parent issue #91 with sub-issues #92-#95.

## Design

- One read-only script, `scripts/msi_review.py` (Python 3.9+, standard library only), with two collectors that build the same model: identities, consumers (resources that hold an identity in `identity` or reference it in another property such as a CMK, Key Vault reference, image pull, or kubelet slot), targets (what each consumer reaches and with which identity), grants (Azure RBAC, Cosmos DB SQL role assignments, Key Vault access policies), and FICs.
- `static <path>` compiles Bicep entry files (files not referenced as modules) with `bicep build --stdout` or `az bicep build --stdout`, reads ARM JSON at any deployment scope (skipping Bicep-generated JSON next to its source), recurses into nested deployments with passed parameters, and evaluates ARM expressions (`parameters`, `variables`, `format`, `concat`, `resourceId`, `extensionResourceId`, `reference(...).principalId/clientId`) and literal resource IDs; unresolved names keep a stable `{param:...}` label and produce MIR000 notes. Terraform is parsed by a brace-aware HCL reader (strings, heredocs, comments) or from `terraform show -json` (`configuration` for references, `planned_values` for map values). `--parameters` accepts ARM parameters JSON (`bicep build-params` output). Source code and `local.settings.json` are scanned for credential classes, token scopes, and service host names; code is attributed to a resource with `--map <dir>=<resource>`, or automatically when there is exactly one app and one Functions project.
- `live --subscription <id>` uses only read-only `az` calls: Resource Graph through `az rest` with a UTF-8 `--body @<file>` (no extension needed), `az role assignment list --assignee-object-id --all --include-inherited --fill-principal-name false` (no Microsoft Graph call), `az identity federated-credential list`, `az webapp config appsettings list`, and `az cosmosdb sql role assignment list` when a Cosmos DB target exists. App setting values are masked except identity settings, GUIDs, and service endpoints, which keep host and path but never the query string; connection strings and SAS URLs are always masked. `--record`/`--replay` store and reuse masked output; `--static <path>` adds drift findings.
- Identity selection follows the platform: Functions connections use `<prefix>__clientId`/`__managedIdentityResourceId`, otherwise the system-assigned identity; SDK code uses `AZURE_CLIENT_ID`, otherwise a setting that holds an attached identity's client ID (longest shared name prefix with the endpoint setting), otherwise the system-assigned identity; Key Vault references use `keyVaultReferenceIdentity`, otherwise the system-assigned identity.
- A grant covers a target when the role is one of the target service's data roles (built-in role IDs and names verified with `az role definition list`; AI-service roles selected by their Cognitive Services data actions) and its scope is the target resource or a broader scope. A grant on a child of the target (container, queue, secret, Foundry project) counts only when the endpoint the consumer uses points into that child. Target names come from setting values, Key Vault reference `VaultName=`/`SecretUri=`, registry login servers, and CMK vault URIs; a `*.servicebus.*` host is Event Hubs when the namespace's resource type says so. SQL, Graph, custom APIs, and Cosmos DB without a data-plane assignment need non-RBAC grants.
- Rules: MIR000 unresolved reference (note); MIR001 identity attached to more than one resource; MIR002 target without a covering grant (error for connections and platform slots, warning when inferred from a URL or code or when the only grant is on a child of the target); MIR003 broad-scope or privileged grant on a shared identity, or a grant only one consumer needs (warning when an FIC exists, otherwise info); MIR004 FIC on an identity that resources use, non-standard FIC audience, or flexible subject matching; MIR005 no client ID where the system-assigned identity is missing (error) or not the intended one (warning), or a client ID that matches none of the resource's identities (warning); MIR006 non-RBAC grant to verify (info); MIR007 code or local settings that run as the developer locally (info); MIR008 drift between Azure and IaC. Exit code 0 when only info and notes remain, 1 for warnings or errors, 2 for input errors.
- Output is a Markdown report (per identity: consumers and their uses, grants and who needs them, FICs; then findings with fixes) or `--json`. `--resource` reviews the identities a resource uses and every other consumer of them; `--identity` starts from an identity (name or resource ID). The skill never creates role assignments, FICs, or identities; fixes are proposed as IaC changes.

## Verification

- `python3 scripts/validate_marketplaces.py` validates the plugin metadata and links.
- `tests/test_msi_review.py` (unittest, runs in the existing Ubuntu `tests` job) covers subscription-scope templates with literal identity IDs; grants on the wrong Key Vault, registry, or child resource; Event Hubs detection; the canonical scenario (storage CMK identity reused by a Function App for Service Bus and trusted by a GitHub Actions FIC) in compiled ARM, Terraform, and Bicep with code (skipped without the standalone `bicep` CLI); identity selection, non-RBAC targets, and custom client ID settings; a clean configuration with no findings; unresolved references; Terraform plan JSON; recorded live output with drift; the ARM expression evaluator, the HCL reader, and masking; and that every rule MIR000-MIR008 has a positive fixture.
- A read-only live run against a real subscription confirmed the `az` arguments, the masking, and the identity inference.
